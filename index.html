Connect your POS to Ownly.

Push your menu, receive orders and keep order status in sync. The guides explain what each integration does; the API reference gives every contract.

Build the integration in this order.

  1. Authenticate your requests.Authentication
  2. Push your menu and handle the processing callback.Menu push
  3. Expose the order endpoint and receive orders.Order relay
  4. Send accepted, cancelled and food ready; receive customer cancellations.Order status exchange
  5. Expose the rider status endpoint and, if you need to call customers or riders, use call masking.Rider status
  6. Keep stock and store availability current.Inventory update

Downstream systems authenticate with Basic Auth. Each contract also lists the request header it expects.

Key header

Auth key

key: <your-auth-key>
Send what each contract lists. Inventory update documents the Authorization header; every other call documents the key header. Keep both server-side and never ship them in a client app or a repository.

How the integration works.

The document is a reference for downstream systems integrating with Ownly for menu, order, order status exchange, item inventory and restaurant status.

Menu integration

Populate a restaurant's menu on Ownly by pushing it from your system. There are no partial updates: every push replaces the existing menu with the new version.

Ownly exposes

An endpoint to publish the menu.

POST /api/v1/menu

Order relay

Every time a customer places an order, Ownly relays the order details to your system.

You expose

An endpoint that receives the order from Ownly.

POST /api/v1/order/

Order status exchange

Once an order is placed it goes through a life cycle, and both systems exchange its status.

Your system pushes order acceptance, order rejection and food ready to Ownly. Ownly pushes the customer cancellation and the rider updates, from assignment to delivery, to your system.

Ownly exposes

An endpoint to receive acceptance, cancellation and food ready from your system.

POST /api/v1/order-status

You expose

An endpoint to receive the customer cancellation from Ownly.

POST /api/v1/order-status

You also expose

An endpoint for rider status updates.

POST <upstream-host>/api/v1/rider-status

Item inventory

Update the stock status of an item, add-on or variant. Your system calls Ownly with the stock details.

Ownly exposes

An endpoint for item inventory status updates.

POST /api/v1/item-status

Restaurant status

Switch a store on or off. Use it to take a restaurant offline when the kitchen is closed or overwhelmed.

Ownly exposes

An endpoint to update store availability.

POST /api/v1/store-status

Call masking

Retrieve a masked contact number and an OTP to start a call between two parties on an order, for example from the restaurant to the customer.

Ownly exposes

An endpoint that returns a masked number and OTP.

GET /api/v1/contact

API reference.

The Ownly API is organised around REST. Every call, grouped by what it manages.

Conventions

Request and response bodies in the samples are JSON. Examples that name a host use https://api.baseurl.com as a placeholder; replace it with the base URL for your integration. Rider status is the exception: it lives on your own host, shown as <upstream-host>.

Success

200A JSON body with a message.

Failure

400A JSON body with an error message. The field is error or message as each contract shows.

Auth

The key header on most calls, Authorization on inventory. See Authentication.

Menu push.

Send the complete menu for a restaurant. Ownly queues it, processes it asynchronously and calls your callbackUrl when it finishes.

POST/api/v1/menu
Ownly hosts thisEvery push replaces the existing menu. There are no partial updates.

Callback

Menu processing is queued and handled asynchronously. Each request is tracked by a unique request id. When Ownly finishes, it calls the callbackUrl from your payload, for example https://<external-host>/callback/<req_id>, with the completion status and the results for that requestId.

Callback request body

ParameterTypeDescriptionRequired
requestIdstringRequest id of the queued menu processing.Required
successboolStatus of the request.Required
errorMsgsstring[]Generic error messages.Optional
dataError object[]Resources that failed, with the type of error, the id of the catalogue entity and the reason.Optional

Error

ParameterTypeDescriptionRequired
resourceIdstringId of the resource that failed.Required
typestringResource type. One of category, subcategory, item, variantGroup, addonGroup, variant, addon, tax, charge.Required
reasonstringThe reason it failed.Required

Item discount

ParameterTypeDescriptionRequired
idstringThe unique identifier of the offer that produced the discount.Required
titlestringThe display name of the offer. For example, "First Off".Required
modestringHow the offer is configured: PERCENTAGE or FIXED. Informational only; use amount for the discount value.Required
valuefloatThe configured discount: a percentage when mode is PERCENTAGE (20 means 20% off), or an amount in currency units when FIXED. Informational only.Required
amountfloatTotal discount for the whole line, in currency units: the item plus all its discounted variants, multiplied by quantity. Equals itemAmount + variantAmount. This is the amount to subtract from the item subTotal.Required
itemAmountfloatThe part of amount that comes from the base item, multiplied by quantity.Required
variantAmountfloatThe part of amount that comes from the item's variants, including nested variants, multiplied by quantity. 0 when no variant is discounted.Required
How item discounts add up
  • For an item with itemDiscounts, unitPrice (item and variants) and the item subTotal are the listed prices before the discount. The amount charged for the line is subTotal − amount.
  • The item total is subTotal − amount + item taxes. Taxes are calculated on the discounted amount.
  • orderInfo.subTotal is the sum of the item subTotal values, before item discounts. orderInfo.total is the amount payable: total = subTotal − item discounts − order-level (CART) discounts + taxes + charges.
  • Discounted variants carry their own discountAmount. Add-ons are not discounted.
  • Item-level discounts are never aggregated into orderInfo.discounts, which only carries order-level (CART) discounts.
  • Items without a discount are unchanged: no itemDiscounts, and the prices are the charged prices.

Order status exchange.

Both systems expose this endpoint to exchange an order's status. Your POS sends acceptance, cancellation and food ready; Ownly sends customer cancellation.

POST/api/v1/order-status
Both systems host thisRestaurant cancellation after acceptance uses this same endpoint.

Request headers

HeaderDescription
keyKey

Request body

ParameterTypeDescriptionRequired
orderIdstringThe Ownly order id.Required
restIdstringThe restaurant id.Optional
statusstringThe new status of the order. See Status values.Required
reasonstringCancellation reason code. Required when status is RESTAURANT_CANCELLED. See Cancellation reason.Conditional
reasonDetailsstringFree-text cancellation details. Required when reason is other. Must not be sent for any other reason.Conditional
metadataOrder status metadata objectOptional metadata for the status update, for example auto-acceptance.Optional
finalPrepTimeintegerFinal kitchen preparation time in minutes selected by the restaurant. Sent with RESTAURANT_ACCEPTED. When prepTimeDetails was present on the order, the value must stay within predictedPrepTime ± the given thresholds.Optional

Status values

ValueSent byMeaning
RESTAURANT_ACCEPTEDYour POSThe restaurant accepted the order.
RESTAURANT_CANCELLEDYour POSThe restaurant cancelled the order. Requires a reason.
FOOD_READYYour POSThe food is ready.
CUSTOMER_CANCELLEDOwnlyThe customer cancelled the order.

Cancellation reason

ValueMeaning
item_out_of_stockOne or more items required for the order are unavailable.
store_closedThe restaurant is closed.
store_busyThe restaurant cannot fulfil the order due to high load.
otherThe cancellation does not match any predefined reason.
Validation rules
  • reason is mandatory for a cancellation.
  • Only the documented enum values are accepted.
  • reasonDetails is mandatory, and must be a non-empty string, when reason is other.
  • metadata.ioos.items is mandatory when reason is item_out_of_stock.
